# Оценка качества HoneyMind

> Главное: **84,9 % точности по классам (45/53; 95 % ДИ Уилсона 73–92 %)** на свежей слепой выборке реальных команд из ловушек Cowrie,
> «опасно/нет» (score ≥ 60): precision 0,94, recall 0,85. Выборка маленькая, размечал один человек, а классы в ней —
> в основном разведка, загрузчики и мусор (см. «Что не проверено»). Это оценка для **того типа трафика, на котором тестировали**, а не гарантия вообще.

## 1. Откуда данные

В публичных логах Cowrie нет меток «опасно / не опасно», поэтому:

* **Обучение** — синтетический корпус из шаблонов (`honeymind/corpus.py`, ~1600 команд, 12 классов). Слабая разметка: метка = класс шаблона.
* **Оценка** — реальные команды атакующих из трёх публичных источников (≈ 560 тыс. введённых команд, 3 714 уникальных):
  суточный дамп CyberLab honeynet (Zenodo 10.5281/zenodo.3687527, 2019-05-18) и два набора логов Cowrie с GitHub (≈ 5,1 млн событий).
  Команды **размечены вручную** одним человеком **до** запуска модели на них.

Политика разметки (зафиксирована заранее):
пустые/непонятные строки, HTTP/SIP-заголовки, «каша» из символов → `benign`; пробы вроде `/bin/busybox ABCDE`, `echo OK`, `>/dir/.x && chmod 777 … && …` (проверка записи/исполнения), меню-слова `enable/system/shell/sh` → `reconnaissance`;
запись бинарника или скрипта через `echo … >>` (дроппер без сети) → `malware_downloader`; прочие спорные строки исключены как `ambiguous` (14 штук: 10 + 2 + 2 в раундах 2, 3 и 4).

## 2. Методика: четыре раунда на свежих данных

Реальный трафик сильно повторяется (одна и та же ботнет-цепочка приходит десятки тысяч раз с мелкими вариациями), поэтому выборки строились так:
команды группируются по «скелету» (числа, IP, URL, hex-серии заменены токенами), и из каждой группы берётся **один** случайный представитель.
Выборка раунда = «новые семейства» (скелет не встречался в прошлых раундах) + «известные семейства, новый вариант» / взвешенная по частоте.

Порядок работы: раунд → **один** запуск → фиксация результата («первый взгляд») → разбор ошибок → общие исправления → следующий раунд на **новых** командах.
Поэтому каждый раунд честен только в момент своего первого запуска; после правок он становится отладочным и перестаёт быть независимым.

| Раунд | n | Версия системы | Accuracy (hybrid) | Danger P / R / F1 (hybrid) | Что показал |
|---|---|---|---|---|---|
| 1 | 150 | первая версия, без знания реального трафика | **22,7 %** | 0,92 / 0,99 / 0,95 | Балл «опасно» почти всегда верный, но классы мимо: 86 из 150 — бинарные дропперы через `echo -ne "\x…" >> file`, для них не было ни правила, ни класса в корпусе; обычные пробы IoT-ботов модель считала «безобидными» или «закреплением» |
| 2 | 140 | после исправлений по раунду 1 | **75,7 %** | 0,75 / 0,85 / 0,80 | Правила `chmod 777 && запуск` ловили пробы записи как вредонос; модель на мусоре (HTTP/SIP-заголовки, случайные слова) выдавала средние баллы |
| 3 | 77 | после исправлений по раунду 2 | **96,1 %** | 0,98 / 1,00 / 0,99 | Одиночный `/` получил 82 («destructive» по n-граммам) |
| 4 | 53 | после исправлений по раунду 3 | **84,9 %** | 0,94 / 0,85 / 0,90 | Финальная версия кода, 95 % ДИ точности 73–92 % |

Раунд 4 — единственное «чистое» число для текущей версии. Раунд 3 (96 %) выглядит лучше, но выборка меньше, а в раунд 4 вошло больше «новых семейств» (43 из 53 против 53 из 77).
Разумно ожидать **85–95 %** на трафике того же типа; на другом трафике — неизвестно.

Текущая версия кода на всех наборах (раунды 1–3 — уже отладочные, цифры там **завышены**):

| Набор | n | rules acc | model acc | **hybrid acc** | hybrid danger P / R |
|---|---|---|---|---|---|
| CyberLab (автор видел до написания правил) | 53 | 0,94 | 0,81 | 0,94 | 1,00 / 1,00 |
| Раунд 1 (отладочный) | 150 | 0,93 | 0,93 | 0,99 | 0,99 / 1,00 |
| Раунд 2 (отладочный) | 140 | 0,82 | 0,92 | 0,96 | 1,00 / 0,98 |
| Раунд 3 (отладочный) | 77 | 0,78 | 0,97 | 0,99 | 1,00 / 1,00 |
| **Раунд 4 (чистый)** | 53 | 0,68 | 0,74 | **0,85** | 0,94 / 0,85 |

Полные метрики: `reports/eval_history.json` («первый взгляд» каждого раунда), `reports/eval_final_code.json` (финальный код), воспроизведение: `python evaluate.py`.

## 3. Что показывают три режима (раунд 4, честный)

* **Только правила**: precision «опасно» 1,00, но точность по классам 68 % и 26 % ответов уходят в `needs_review` (правило не сработало). Правила — надёжная «первая линия», но покрывают мало.
* **Только модель**: точность 74 %, зато закрывает «дырки» правил; сама по себе слишком часто объявляет опасным мусор (precision 0,67).
* **Гибрид** лучше обоих по точности классов (85 %), но по «опасно/нет» **не лучше правил** (recall тот же 0,85; precision 0,94 против 1,00): модель в основном улучшает разбор безопасных/мусорных строк и классов, а не ловит больше опасного.
  Оба режима пропустили одни и те же три опасные команды: `sh /tmp/.ds` (запуск скрытого скрипта по полному пути) и два дроппера, собранных через `/bin/busybox echo -ne` (правила ждут `echo` в начале строки).

Ошибки раунда 4 (8 из 53) — `sh /tmp/.ds` (балл 40, нужно ≥ 60), `cat $pid/comm` и `cat` (credential_access 40 вместо recon/benign), `Enter new UNIX password: ` (60), `12345` (reverse_shell 40, мусор),
три дроппера через echo: два — пропуски (балл 30–40), третий — верное «опасно», но класс `malware_execution` вместо `malware_downloader`. Исправлять по ним дальше значило бы подгонять под тест — это ровно то, чего избегала методика.

## 4. Что НЕ проверено (важно)

* **Редкие классы почти отсутствуют в реальных данных**: `reverse_shell`, `cryptominer`, `destructive`, `credential_access`, `network_scan`, `privilege_escalation` — в 3 714 уникальных командах их единицы.
  Аудит всех предсказаний этих классов на реальном пуле (15 уникальных строк): верный класс у 3 (`su`, `sudo /bin/sh`, сканер `zgrab`);
  ещё 3 — опасные дропперы через `/dev/tcp`, названные `reverse_shell` (класс неверный, «опасно» верно); остальные 9 — ложные срабатывания на мусоре или чистке файлов:
  у 5 балл ≤ 40, у 4 — ≥ 60 (`rm -rf *.sh; …` ×2 — 82 и 88, `cat /etc/*release*` — 73, `Enter new UNIX password: ` — 60).
  Для этих классов у нас есть только синтетика и юнит-тесты — реальную точность назвать нельзя.
* **Один разметчик**, нет проверки согласия (inter-annotator agreement). Граничные случаи (пробы записи, построчная сборка скрипта) — спорные; другая политика разметки сдвинет цифры на несколько процентов.
* **Три источника, всё — SSH/Telnet-ловушки Cowrie** с трафиком IoT-ботнетов. Распределение в HoneyForge (другие приманки, веб-ловушки, живые операторы) будет другим.
* **Малые n**: 53–150 уникальных команд на раунд; доверительные интервалы 5–15 п. п.
* **Метрики по уникальным командам, а не по трафику**. Взвешенная по частоте точность раундов 3–4 ≈ 99,5 % — «голова» распределения (повторяющиеся цепочки ботов) классифицируется почти безошибочно; хвост — труднее.
* **`is_human` на реальных людях не проверен** — см. раздел 5: в данных нашлась лишь одна сессия, похожая на человека.
* Оценка входов по паролю и загрузок — эвристики, отдельно не оценивались.

## 5. `is_human`: «человек или бот» по сессии

### 5.1 Факты о данных
* Просмотрено ≈ 338 тыс. реальных сессий Cowrie (два набора с GitHub). Из 27 492 сессий с ≥ 4 командами только **59** имели
  последовательность команд, которой нет в других сессиях; остальные — тиражируемые скрипты.
* Все 59 уникальных просмотрены вручную (один человек): **58 — боты**, **1 похожа на человека**
  (`we` → `w` → `whomai` → `clear` → `ls` → `free -h`, паузы 0,6–2,9 с — опечатки и исправления). Она вынесена в `data/real_suspected_humans.json`
  и исключена из «ботов». Найдена она, кстати, моделью — уже после обучения, на тестовой части.
* «Человечные» метаданные не помогают: все 23 сессии, запросившие размер терминала, — боты (JSCH, phpseclib); клиенты OpenSSH/PuTTY команд не вводили.
* Вывод: **людей для обучения в публичных логах нет** → люди симулируются, боты берутся настоящие.

### 5.2 Методика
* Люди — `honeymind/simulate.py`: время = «подумать» (логнормальное) + «набрать» (∝ длине команды) + «прочитать вывод»; опечатки с исправлением;
  цели: осмотреться / найти секреты / закрепиться / «админ»; 15 % — вставляют кусок готового скрипта (внутри куска темп как у бота);
  25 % — «минималисты» (короткий набор разведки без навигации, как у бота).
* Боты — **реальные** сессии Cowrie (≥ 4 событий; не больше 3 сессий от одного сценария), плюс синтетика: мгновенные, «ждущие ответа» с почти равными паузами,
  с таймаутами, со случайным «человеческим» темпом, чистый подбор паролей.
* Реальные боты делятся на обучение/тест **по сценарию** (один скрипт не попадает в обе части): 210 сессий в обучении, 176 сессий / 87 сценариев в тесте.
* Порог «человек» подбирается по out-of-fold вероятностям на обучении: минимальный, при котором ни один реальный бот (с ≥ 3 командами) не становится «человеком». Получился 0,81.
* Проверка людей — на отдельной симуляции (другое зерно) + «сдвинутые» люди (быстрее печатают, почти без опечаток, чаще вставляют из буфера)
  + два вида, которых **не было в обучении**: бот-подражатель (паузы как у человека + `ls`/`cd`) и (в отдельном прогоне) люди-«минималисты».
* Модель: логистическая регрессия, 23 признака, C = 0,1. Сильная регуляризация выбрана ради осмысленных весов (при C = 1 часть весов меняла знак
  из-за взаимозависимости признаков); на метрики это повлияло слабо. Оговорка: тестовые отчёты я видел при выборе — это не чистый слепой тест.

### 5.3 Результаты (`reports/human_eval*.json`)

| Набор | «человек» | «бот» | «не знаю» |
|---|---|---|---|
| **Реальные боты, тест** (176 сессий, 87 сценариев) | **0 %** (95 % ДИ сверху ≈ 2,1 % по сессиям / 4,2 % по сценариям) | 97,7 % | 2,3 % |
| то же, старая эвристика по темпу | 7,4 % | 65,9 % | 26,7 % |
| Реальная сессия, похожая на человека (n = 1) | **да, p = 0,92** | | |
| Симуляция: люди / «сдвинутые» / вставляют скрипт / «минималисты» | 100 / 92,7 / 100 / 83,3 % | ≤ 2,7 % | остальное |
| Симуляция: боты мгновенные / ждущие / таймауты / брутфорс | 0 % | 65–98 % | остальное (часто < 4 событий) |
| Симуляция: бот со случайным темпом | 0,6 % | 64 % | 35 % |
| **Бот-подражатель (не было в обучении)** | **28 %** | 14 % | 57 % |

Что это значит:
* **На реальных ботах модель надёжна** — и это главное: люди редки, поэтому даже 1 % ложных «человеков» на 240 тыс. сессий дал бы тысячи ложных тревог.
* **Модель знает только тех людей, которых мы описали.** Контрольный прогон без «минималистов» в обучении (`reports/human_eval_ood.json`) узнавал их лишь в 54 % —
  значит, люди нового, непредусмотренного типа будут чаще получать `null`/«бот».
* **Подражателя не поймать поведенческими признаками** в принципе: если скрипт делает паузы и ходит по папкам, он выглядит как человек.
  Помогает трекер сценариев (одинаковый подражатель с разных IP) — но не против уникального.
* Сравнение с градиентным бустингом (`reports/human_eval_hgb.json`): на симуляции лучше (99,7 % «минималистов»), но подражатели проходят в 66 %,
  а реальную «человеческую» сессию он оценил в p = 0,13. Симптом переобучения на симулятор → оставлена логистическая регрессия (оговорка: решение по n = 1).
* Симулятор написан тем же человеком, что и признаки, — проверки на симуляции частично проверяют сами себя. **Настоящая проверка — сессии живых людей**
  (`scripts/eval_sessions.py`, протокол в README).

## 6. Как улучшать

1. Собрать трафик собственных ловушек HoneyForge и разметить 300–500 команд **двумя** людьми; считать согласие и тестировать на нём (метки из бэкенда после ручной проверки в панели: `needs_review` как очередь разметки).
2. Дообучать на реальных размеченных данных, оставляя синтетику только для редких классов.
3. Для редких классов собрать реальные примеры из отчётов (Mirai/Gafgyt/Kinsing и т. п.) и добавить в `evalset`.
4. Подумать над калибровкой вероятностей (`CalibratedClassifierCV`) и над отдельным «не команда»-классом вместо набора эвристик для мусора.
